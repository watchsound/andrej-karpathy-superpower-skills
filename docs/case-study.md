# Baking Discipline Into AI Coding Agents: A Case Study

*How a fork of a popular skill library turned three theoretical failure modes into measurable wins — and what happened when the eval caught a problem that the design had silently introduced.*

---

## Part One: Why This Exists

In January 2026, Andrej Karpathy posted a short observation on X that hit harder than most of his explainer threads ever do. He was describing what it actually feels like to work alongside a frontier language model on real code, day after day. The headline complaint was not that the models were stupid, or unhelpful, or slow. The headline complaint was that they were *confidently wrong in a particular way*.

"The models make wrong assumptions on your behalf and just run along with them without checking," he wrote. "They don't manage their confusion, don't seek clarifications, don't surface inconsistencies, don't present tradeoffs, don't push back when they should. They really like to overcomplicate code and APIs, bloat abstractions."

If you have spent any significant amount of time pair-programming with a model, you have felt every word of that. It is not a fairness issue or a capability issue. It is a *discipline* issue. The model is perfectly capable of asking the right clarifying question. It is perfectly capable of writing the simplest possible code. It is perfectly capable of stopping when an assumption is load-bearing and unverified. It just doesn't, by default. The same model that will produce a tight, surgical fix when prompted carefully will, on the next request, refactor four unrelated functions, introduce a new abstraction layer, and confidently assume a database schema that does not exist.

Karpathy's observation got picked up quickly. Forrest Chang distilled it into a four-rule preamble suitable for a `CLAUDE.md` file: think before coding, simplicity first, surgical changes, goal-driven execution. That preamble became a small viral artifact in the AI-coding-tools corner of the internet. It crossed a hundred thousand stars on GitHub in a few months. People reported it actually helped.

But a preamble has a problem that nobody talks about. A preamble fires *once*, at the start of the session. Every skill the agent invokes, every tool call it makes, every paragraph of context that gets loaded — all of those compete with the preamble for attention budget. By the time the model is deep in a debugging session three hundred turns in, the four rules at the top of the context window are functionally background noise. The discipline has decayed.

There is a separate library called Superpowers, maintained by Jesse Vincent and Prime Radiant, that takes a different approach to the same problem. Instead of one preamble, Superpowers gives the agent a *workflow*. There is a skill for brainstorming, a skill for test-driven development, a skill for writing implementation plans, a skill for systematic debugging, a skill for receiving code review. Each skill auto-triggers when the agent's situation matches its description. Each skill carries its own internal discipline — the TDD skill makes you watch the test fail before writing implementation; the brainstorming skill refuses to let you write code before a design has been approved.

Superpowers is good. It is, by some distance, the most thoughtful piece of behavior-shaping infrastructure I have used with Claude Code. But it was designed before Karpathy's January post, and it does not address the moment-to-moment failure modes that post described. The Superpowers TDD skill will make you write a test first, but it will not stop you from making an unstated assumption about what the function is supposed to do. The brainstorming skill will make you present a design before writing code, but it will not stop you from designing the wrong feature because you misunderstood what the user meant by "order."

The question this fork tries to answer is: *what if we baked the four rules into each skill's body, so the discipline fires exactly when the skill fires, exactly where it can shape behavior?* Not as a preamble at the top of the context window, but as a small reinforcement clause inside each skill — invoked at fire-time, when the model is already paying close attention to that skill's content.

That is the first motivation. The second is older and more familiar. Anyone who has worked on a long-running project with an AI agent has watched it happen: the vocabulary drifts. The model uses "user" and "account" and "customer" interchangeably in week one, and by week three nobody can tell if "the user record" means the auth system's row, the billing system's stripe customer, or the analytics system's anonymized profile. The drift is invisible — each turn looks fine in isolation — and the cost is invisible until something breaks, usually weeks later, usually in production. Matt Pocock has a small skill in his own library that addresses this with a runtime-built glossary called `CONTEXT.md`. The agent reads it at session start, refers to it during work, and updates it inline whenever a new term gets pinned down. It is one of those design choices that looks too simple to matter and turns out to matter enormously. We absorbed his mechanism — not by vendoring his skill as a peer, which would have added a new top-level skill to the library, but by folding the ritual into the existing `brainstorming` skill where it naturally belongs.

The third motivation is the one that took the longest to surface. It came from frustration with my own past TDD work. I had, over many years, accumulated codebases full of beautifully tested units that composed into bad architectures. The unit tests all passed. Each component did exactly what its tests said it should do. But the whole system was brittle, hard to extend, and full of seams in the wrong places. Bottom-up TDD has a documented failure mode that Uncle Bob and others have written about: when you start from leaves and work up, you commit to the architecture last, and by then the cost of getting it wrong is paid out in retrofitting. The standard fix in industry is some flavor of London-school TDD, which uses heavy mocking to start at the top. The mocking has its own costs. We wanted to import the *ordering discipline* of outside-in TDD — start at the architectural boundary, not the leaf utility — without importing the mocking baggage.

That third motivation translated, in the end, into something we called the Architecture-Driven Design harness. Architecture remains the boss. TDD is the worker. The discipline is not concentrated in the TDD skill, which would have overloaded it; instead it is distributed across the three skills that own each stage of the workflow. Brainstorming gains a Walking Skeleton subsection that fires for greenfield work. Plan-writing gains a Contract-First rule that requires interface definition before any test gets written. TDD itself gains an outside-in ordering clause — the next failing test always targets the highest-uncovered architectural boundary — but keeps its existing rule against London-school mocking. Each piece lives where it can fire at the right moment.

Those three motivations — Karpathy's discipline, Pocock's vocabulary, the architecture/TDD harness — gave the fork its shape. The work that followed was an attempt to express each of them surgically inside the existing Superpowers skill set, without creating a sprawl of new skills and without rewriting the carefully tuned content the upstream maintainers had already eval'd to a high bar.

## Part Two: The Three Failure Modes in Detail

Let's slow down and look at each failure mode more carefully, because the fix has to fit the problem.

The first failure mode — the Karpathy mode — is what I think of as *silent assumption*. The model has a question it does not know it has. It picks one interpretation of an ambiguous input and proceeds confidently. It might be exactly right. Often it is. But when it is wrong, the wrongness is not surfaced until much later, when the divergence between what the user wanted and what the model built has compounded across many turns. The cost of asking would have been thirty seconds. The cost of not asking is sometimes the entire session.

This failure mode is amplified by reinforcement learning. Models are rewarded for being helpful, and asking clarifying questions can feel like *not* being helpful. They are rewarded for producing visible output, and silence-and-think can feel like *not* producing output. The path of least resistance is to guess, generate, and move on. Karpathy's four rules push directly against that gradient. Think before coding means surface assumptions, ask clarifying questions, present tradeoffs. Simplicity first means resist the urge to add features that were not asked for. Surgical changes means do not refactor adjacent code while you are at it. Goal-driven execution means know what success looks like before you start.

These rules are easy to write down and hard to enforce. They contradict the model's defaults at every turn. A preamble can remind the model they exist, but a reminder competes with everything else in the context window. The natural enforcement mechanism is the skill body itself — every time the TDD skill fires, every time the brainstorming skill fires, every time the debugging skill fires, the relevant rules fire too, with concrete examples of how they apply to *that specific stage of work*. The reinforcement happens at the moment of attention, not at session start.

The second failure mode — semantic drift — is structurally different. It is not a per-turn discipline failure; it is a cross-turn coherence failure. Each turn, the model uses a word that seems reasonable in isolation. Across turns, the same word picks up different meanings, and nobody notices until something goes wrong.

A concrete example. You are designing an order book for a Chinese A-share trading system. You say "order." The model writes down some assumptions about what an order is — its fields, its lifecycle, its identity. In the next turn you talk about the call auction. The model treats "order" the same way. In the third turn you mention purchase orders for the back-office accounting integration. The model is now confused but does not surface it. By the time you are writing tests, the word "order" in the code means three different things, and the codebase will look fine but will be quietly inconsistent in ways that cause bugs months later.

The defense is a *project-specific glossary that is built at runtime, not pre-curated*. Pre-curation does not work — you cannot enumerate every domain term before you have explored the design. Runtime curation is what humans do naturally on real teams: a term comes up, somebody pins it down, the team adopts it, drift is bounded. The CONTEXT.md mechanism is the runtime-curation pattern translated for AI agents. The agent reads it at session start. When the user uses a fuzzy or overloaded term, the agent stops and disambiguates. When a term is resolved, the agent writes it back to the glossary inline — not batched, not at the end of the session, but immediately, while attention is still on the term. Refusal to use technical jargon like Manager, Processor, Helper, or Utils when a domain term exists is part of the discipline; those names are signals that you have not understood the domain yet.

The third failure mode is the most subtle and the hardest to convince people of. Bottom-up TDD looks like it works. Every test passes. Every unit is well-defined. The test suite is fast and reliable. What is missing is invisible: the *architecture is committed to last*, by accretion, rather than first, by design. You discover the seams of your system after you have already built the pieces. You discover the boundaries between modules after you have already written code that crosses them. The cost is paid out later, when you need to extend the system and find that the natural extension points do not exist.

Uncle Bob wrote about this in 2017 in a piece titled "TDD Harms Architecture." His critique was specific: bottom-up TDD produces over-isolated tests and design fragility, because unit tests mock dependencies without verifying that the actual integration is sound. London-school TDD addressed this by inverting the direction — start at the top, mock everything below — but the mocks themselves coupled tests to implementation in a different way, and the cost of refactoring went up.

We wanted the *ordering discipline* of outside-in TDD without the *mocking commitment* of London-school. Outside-in ordering says: write the test for the architectural boundary first, before you write any helper. That forces the boundary to be defined before you commit to internals. Then, when you drill into a helper because the boundary test cannot pass without it, you write the helper with real code, not a mock. The existing TDD rule against mocking everything in sight still applies. The new rule just changes *which test you write first*.

Greenfield work has an additional move available. Before you write any test at all — even the boundary test — you build a Walking Skeleton: an end-to-end thin slice through every architectural layer with zero business logic in any of them. The skeleton proves that the layers can be wired together. The seams between them are defined as concrete interfaces. There is one acceptance test that exercises the whole pipeline. Only after the skeleton is approved do you start designing features that will plug into the seams. This is the architectural commitment, made first, validated immediately, before any TDD cycle runs.

Each of these three failure modes has its own shape, and the fix has to match the shape. Karpathy's discipline is per-turn and needs reinforcement at fire-time. Semantic drift is cross-turn and needs a glossary that is read, updated, and consulted continuously. Architectural failure is up-front and needs a skeleton or a contract before any code gets written. Different shapes; different mechanisms.

## Part Three: The Design Philosophy

Once the three failure modes were clear, the question became *where to put the fix*. The Superpowers library already had seventeen skills. Adding three more for each of these three problems would have been the obvious move, and probably the wrong one.

There is a real cost to adding skills. Each one is a description that has to be read, an auto-trigger condition that has to compete with every other skill's auto-trigger condition for the right moment, a body of text that has to be loaded and attended to when it fires. Skill sprawl is the AI-agent equivalent of microservice sprawl — at some point the coordination overhead exceeds the benefit, and the model starts making mistakes about which skill applies. The thoughtful upstream maintainers had been deliberate about keeping the library compact. We wanted to honor that.

So the design constraint became: *fold the new discipline into existing skills wherever possible. Create a new skill only when no existing skill has the right semantic ownership of the problem.*

Karpathy's four rules fit nicely under that constraint. Every existing skill in the library had a specific stage of work where some subset of the four rules applied with particular force. The TDD skill needed reinforcement on simplicity first (GREEN means minimum code, not speculative features), surgical changes (do not touch unrelated code during RED-GREEN), and goal-driven execution (the failing test is the success criterion). The brainstorming skill needed reinforcement on think before coding (surface every assumption about scope and intent) and goal-driven execution (the design must produce verifiable success criteria). The systematic-debugging skill needed think before coding (name what you do not understand instead of guessing), surgical changes (fix only the root cause), and goal-driven execution (reproduce the bug with a failing test first).

Rather than write the same four-rule preamble at the top of every skill, we wrote a short *Karpathy Reinforcement* block at the top of each relevant skill body — three or four lines specific to that skill, listing only the rules that materially strengthen its behavior, with a one-line note explaining how each one applies *in this specific stage of work*. The full text of the four rules lives in a separate `karpathy-guidelines` skill that loads on demand. Each reinforcement block ends with a pointer there for the full text.

The semantic-drift fix was harder to place. CONTEXT.md is read at session start, consulted throughout, and updated as terms emerge. None of the existing skills owned that lifecycle. But brainstorming was the closest fit — it was the first skill to fire on any new feature work, it already had a "Explore project context" step in its checklist, and it was the natural place for design-level naming decisions to get pinned down. So we folded the Ubiquitous Language ritual into brainstorming as a new subsection: read CONTEXT.md at session start, disambiguate fuzzy terms inline, write resolved terms back immediately, refuse technical jargon when a domain term exists. Three other skills — executing-plans, receiving-code-review, systematic-debugging — got a one-line cross-reference to consult the glossary at their own decision points, so the discipline does not get bypassed downstream.

The architecture/TDD harness was the hardest distribution problem. The temptation was to concentrate all of it in the TDD skill, which would have ballooned that skill to twice its size and changed its character from "discipline for the inner loop" to "discipline for the whole pipeline." We pushed back against that temptation. The Walking Skeleton concept belongs in *brainstorming*, because the skeleton is a design artifact — it is presented as part of the design phase, before any test gets written. The Contract-First rule belongs in *writing-plans*, because the contract is a plan structure — Task 1 defines the interface, Task 2 writes the boundary test, Task 3 implements under TDD. The outside-in ordering rule belongs in *test-driven-development*, because it is a TDD-cycle rule — which test do I write next. Each piece in the skill that owns that stage of the workflow.

This distribution had a second benefit beyond not bloating TDD: it made the fork's discipline operate at multiple checkpoints across a project's lifecycle. The Walking Skeleton fires once, in brainstorming, when the project is greenfield. The Contract-First rule fires per-module in plan-writing. The outside-in ordering fires per-test in TDD. Three independent enforcement points, each at the right level of granularity.

The three new skills we did add — `karpathy-guidelines`, `prefer-deterministic-code`, `token-budget-discipline` — passed the test of having no existing semantic owner. The karpathy-guidelines skill exists because the full four-rule text needs to be loadable on demand by any other skill that references it; that is a vendoring role, not an inline-extension role. The prefer-deterministic-code skill exists because no existing skill addresses the failure mode of wrapping an LLM call around a deterministic question (routing, retries, status codes); it is a new behavioral guardrail with no obvious home. The token-budget-discipline skill exists because no existing skill addresses unbounded agent loops; checkpoint-and-restart is a meta-discipline that operates across other skills, not within any one of them.

Beyond those three, every other behavioral addition was inline. The TDD skill gained six new sections — Karpathy Reinforcement, Test Quality Bar, Where to Start the Cycle, Behavior Not Implementation, Test Organization and Traceability, Layered Tests — without losing a single line of its original tuned content. The brainstorming skill gained Karpathy Reinforcement, Ubiquitous Language, and Walking Skeleton without losing its core checklist. The writing-plans skill gained Karpathy Reinforcement and Architecture Contracts First. The executing-plans skill gained Karpathy Reinforcement and Checkpoint Discipline. And so on across thirteen existing skills, with one — `using-git-worktrees` — deliberately untouched because it is purely mechanical and gains nothing from behavioral reinforcement.

There was also a piece of personal-engineering-standard content that did not fit in any skill: a mandatory response format requiring every code-modifying response to end with a *Discovered Issues* section (bugs noticed in adjacent code but not fixed) and an *Assumptions Made* section (every assumption taken to proceed, with critical markers on load-bearing ones). That lives in `CLAUDE_APPEND.md` at the project root, with a note that it should be appended to user-global `CLAUDE.md` or project-level `CLAUDE.md`. It is the only piece of the fork that operates at the prompt-preamble level rather than the skill level. Its job is to make the four Karpathy rules visible at the end of every response — a kind of audit trail that the rules actually fired.

## Part Four: What Was Built

This section walks through the additions concretely, in the order they fire during a typical project lifecycle.

When a fresh session opens, the first skill to engage is *using-superpowers*, the bootstrap. It gained a new Karpathy Baseline subsection at the end, listing all four rules as a permanent lens for every session. This is the closest thing to a preamble in the fork — but it lives inside a skill that the agent has explicit reason to attend to, rather than at the top of the prompt where it competes with everything else.

The next skill to fire on any creative work is *brainstorming*. This is the skill that gained the most new content. Three additions sit above the original body, in attention-priority order. The first is the Karpathy Reinforcement block: two rules (think before coding, goal-driven execution) presented with concrete application notes — surface every assumption about scope and intent in the design itself; the design must produce verifiable success criteria, not vague intent. The second is the Ubiquitous Language section: read CONTEXT.md at session start, disambiguate fuzzy terms inline, refuse technical jargon when a domain term exists, write resolved terms back to the glossary as they emerge. The third is the Walking Skeleton section: when the design is for a new system or service, the first design deliverable is an end-to-end thin slice with zero business logic, proving every layer is wired before any feature is designed.

The brainstorming checklist itself was extended by one step — read CONTEXT.md — and a clause was added to the "Present design" step explicitly requiring a Walking Skeleton as the first section for greenfield work. That clause was not in the original draft. It was added after the first round of evaluation revealed that the original Walking Skeleton subsection did not reliably fire, because by the time the agent reached the "Present design" checklist item, the subsection's guidance had drifted out of attention. We will come back to this in the validation section.

The next skill in the flow is *writing-plans*. Its main behavioral addition is the Architecture Contracts First section: for each new module or boundary the plan introduces, Task 1 defines the interface (type, abstract class, schema, protobuf) with no implementation; Task 2 writes the boundary test that exercises the component through its public interface only; Task 3 and beyond implement under TDD to satisfy the contract. The reason for this ordering is that it forces the architecture to be committed to before TDD runs. TDD then operates as a worker fulfilling an already-defined contract, rather than as a designer inventing one bottom-up. The plan-writing skill also gained Karpathy Reinforcement on think-before-coding and goal-driven-execution: ambiguity left in the plan becomes ambiguity in execution; each plan step must carry a verifiable check, not just a description of the action.

The skill that fires most often during implementation is *test-driven-development*. This is the skill that the original Superpowers maintainers had tuned most carefully — an Iron Law (no production code without a failing test first), an explicit Red-Green-Refactor cycle, a Red Flags table, a Common Rationalizations table, a Final Rule. We were very careful with this skill. The new content was added as supplementary sections, in two waves. The first wave, at the top of the skill, is Karpathy Reinforcement and Test Quality Bar — both short, both high-leverage, both complementary to the Iron Law rather than competing with it. The Karpathy Reinforcement focuses on simplicity-first (GREEN means the minimum code that makes the test pass, not speculative features), surgical-changes (do not touch unrelated code during RED-GREEN), and goal-driven-execution. The Test Quality Bar says: a test must encode why the behavior matters, not just that the function returned something. If a developer could replace the function body with `return constant` and the test still passes, the test is worthless. A short checklist follows: does the assertion depend on the input or on a constant; does the test fail if the business rule changes; could a buggy implementation that swallows errors still pass it.

The second wave of TDD additions sits at the bottom, under a single Reinforcement heading, after the original Final Rule. Where to Start the Cycle says: the next RED test targets the highest-uncovered architectural boundary, not the lowest utility — outside-in *ordering*, not London-school mocking, with a Q&A table explaining when to mock and when not to. Behavior, Not Implementation forbids assertion shapes that interrogate internals (toHaveBeenCalledTimes, toHaveBeenCalledWith, private-field reads) and introduces mutation thinking as the green-test verifier: before accepting a green test, mentally mutate the source — what if `+` became `-`, what if `<` became `<=`, what if errors got swallowed — and write another test if any of those mutations would not be caught. Test Organization and Traceability says: colocate test files with sources, name tests using CONTEXT.md canonical terms, tag tests by bounded context, run related-tests during iteration and the full suite at the completion gate. Layered Tests says: most tests are domain/unit tests (pure logic, no I/O, milliseconds); a thin layer of integration tests sits above; if you find yourself mocking five or more dependencies to test one function, the *design* is wrong, not the test.

The structural choice of putting these reinforcement sections at the bottom rather than the top was deliberate. The original Iron Law is the foundation. A reader, human or model, who only attends to the first few hundred lines of the skill should still encounter the unconditional core. The reinforcement sections sharpen the cycle but never override it. That ordering decision came directly from the evaluation feedback — an earlier draft had all the reinforcement at the top, and the Iron Law sat hundreds of lines down, which is exactly the attention-budget anti-pattern we were trying to avoid in the first place.

The *executing-plans* skill gained Karpathy Reinforcement (simplicity-first, surgical-changes, goal-driven-execution, plus a consult-the-glossary bullet) and a new Checkpoint Discipline section. After each plan step, the agent writes a four-line summary: Done (what edits this step produced), Verified (which checks passed, with command plus observed output), Remaining (the next concrete step). The self-check before starting step N+1 is explicit: did I write the checkpoint, does Verified cite a command and its output, does Remaining match the plan. If any box fails, do not advance. The TodoWrite mechanism and Checkpoint Discipline are deliberately distinguished — TodoWrite tracks which task you are on; the Checkpoint Discipline tracks what state the task left the codebase in. Marking a TodoWrite item complete without writing the checkpoint is the failure this skill exists to prevent.

The *systematic-debugging* skill gained Karpathy Reinforcement (think-before-coding to name what you do not understand instead of guessing; surgical-changes once the root cause is found; goal-driven-execution to reproduce the bug with a failing test before fixing) and two extra bullets: disambiguate via CONTEXT.md before forming hypotheses, and bound the loop via token-budget-discipline so long debugging sessions checkpoint rather than thrashing.

The *receiving-code-review*, *requesting-code-review*, *finishing-a-development-branch*, *dispatching-parallel-agents*, *subagent-driven-development*, *verification-before-completion*, and *writing-skills* skills each gained a small Karpathy Reinforcement block scoped to the rules that matter most for that stage of work. Receiving-code-review picked up two rules (simplicity-first and surgical-changes, with a defer-to-the-glossary bullet for naming disputes). Requesting-code-review picked up think-before-coding. Finishing-a-development-branch picked up surgical-changes. Dispatching-parallel-agents and subagent-driven-development picked up think-before-coding and goal-driven-execution. Verification-before-completion picked up goal-driven-execution. Writing-skills picked up think-before-coding, simplicity-first, and goal-driven-execution. In each case the block is three or four lines, listing only the rules that materially strengthen the skill's behavior, with one-line application notes.

Three new skills round out the additions. The *karpathy-guidelines* skill is a verbatim vendor of Forrest Chang's four-rule CLAUDE.md (MIT-licensed, attribution preserved at the top of the file). It loads on demand so the full rule text is available to any skill that cross-references it. The *prefer-deterministic-code* skill refuses to wrap an LLM call around a question with a deterministic answer — routing, retry decisions, status code handling, type checks, validation, transformations a regular function can express. Its core principle is short: a flaky LLM call is worse than deterministic code when the question has a single right answer. The skill includes a decision flowchart, good and bad use examples, and a Red Flags table. The *token-budget-discipline* skill establishes explicit per-task and per-session budgets (defaults: 4K soft / 8K hard per task, 30K soft / 60K hard per session) with checkpoint-and-restart discipline. Its core principle is also short: bounded loops that checkpoint beat unbounded loops that drift.

The `CLAUDE_APPEND.md` file at the project root contains the Mandatory Response Format described earlier. It is meant to be appended to a user-global or project-level CLAUDE.md. Every code-modifying response ends with two sections, omitted if empty: Discovered Issues (bugs noticed but not fixed, with file:line and a short description) and Assumptions Made (every assumption taken, with critical markers on the load-bearing ones).

That is the full set of additions. Three new skills, one preamble file, behavioral reinforcement folded inline into thirteen existing skills, one new reference file for the CONTEXT.md format. The smallest possible footprint that delivers the three motivations.

## Part Five: The Hardest Decisions

Most of the work in this fork was not about *what* to add but about *how* to add it — specifically, how to add it without breaking the carefully tuned content the upstream maintainers had already eval'd. The Superpowers contributor guidelines have a section explicitly warning that skills are not prose, they are *code that shapes agent behavior*, and that modifications without before/after eval evidence have a very high bar. Some of the hardest design decisions came out of trying to honor that constraint.

The first hard decision was about outside-in TDD. The natural way to import outside-in TDD into the library would have been to lean on London-school mocking — start at the top, mock everything below, build up to the implementation. But the existing TDD skill had a strong, well-tuned rule against mocking when you can avoid it. Real code beats mocks. Mocks couple tests to implementation. The London-school approach directly contradicted this. So we made a deliberate choice: import the *ordering discipline* without the *mocking commitment*. The new rule says the next RED test targets the highest-uncovered architectural boundary; when you drill into a helper, you write it with real code, not a mock; mocks are reserved for genuinely external layers (network, filesystem, time). That is outside-in *ordering* applied to a non-London-school TDD style. We had to write that explicitly in the skill, because the obvious interpretation would have been the London-school one.

The second hard decision was about distributing the Architecture-Driven Design discipline across multiple skills rather than concentrating it. The temptation was to make TDD the home for everything architectural — write a longer TDD skill that covered Walking Skeleton, Contract-First, and outside-in ordering all in one place. We resisted because of two failure modes that pattern would have produced. First, an overloaded TDD skill would have stopped being about the inner loop and started being about the whole pipeline, losing focus. Second, an architectural decision belongs at the moment of architectural commitment — and that moment is not when you write your first test; it is when you propose your design (in brainstorming) and structure your tasks (in plan-writing). The Walking Skeleton fires in brainstorming because that is where greenfield design happens. The Contract-First rule fires in plan-writing because that is where the task decomposition gets locked in. The outside-in ordering fires in TDD because that is where the next-test decision gets made. Three different decisions; three different homes.

The third hard decision involved the Walking Skeleton trigger language. The original draft of the Walking Skeleton subsection described its trigger softly: "When the design is for a new system or service — not a feature added to an existing codebase — the first design deliverable is a Walking Skeleton." That language is correct, but it is *descriptive*, not *directive*. It assumes the model will read the subsection, evaluate the condition, and act accordingly. In practice, as we will see in the validation section, this was not what happened. The model would read the brainstorming skill top-to-bottom, complete its checklist, and at the "Present design" step go straight into the data model without ever revisiting the Walking Skeleton subsection. The subsection's guidance had drifted out of working attention by the time it mattered. The fix was to pull the trigger directly into the checklist step: a Greenfield Gate clause that says, in directive language, that if the user's request describes a new system, project, or codebase that does not already exist on disk, the first section of the design MUST be a Walking Skeleton, and no data-model section, file layout, or component breakdown may be presented before the Walking Skeleton is presented and approved. We also rewrote the subsection's own trigger language from descriptive to directive: "TRIGGER (no judgment call): apply this whenever the user's request describes a new system, service, project, library, codebase, or product that does not already exist on disk."

The fourth hard decision was about how to introduce the Karpathy Reinforcement blocks. Two alternatives existed. One was to write a long, comprehensive block at the top of each skill that fully restated all four rules and how they apply. The other was to write a short, three-or-four-line block that named only the rules that mattered for that skill, with one-line application notes, plus a pointer to the karpathy-guidelines skill for full text. We chose the short version for an attention-budget reason: a long block at the top of every skill would have pushed the original tuned content down the page, exactly the failure mode we were trying to avoid. The short version reinforces the rules at fire-time without crowding out the rest of the skill's body.

The fifth hard decision concerned the test-driven-development skill's section ordering. An earlier draft put all the new sections — Test Quality Bar, Where to Start the Cycle, Behavior Not Implementation, Test Organization and Traceability, Layered Tests — at the top, before the original Overview, Iron Law, and Red-Green-Refactor cycle. The thinking was that the new content was *added value* and should be visible first. The cost was that the original Iron Law, which had been the unconditional foundation of the skill for years, ended up sitting at line one hundred and fifteen of a four-hundred-and-sixty-line skill. An agent reading top-to-bottom would burn its attention budget on reinforcement before reaching the foundation. We re-architected: Karpathy Reinforcement and Test Quality Bar stay at the top (short, high-leverage, complementary), the original Iron Law and Red-Green-Refactor cycle come next, and the four longer reinforcement sections move to a single Reinforcement block after the original Final Rule, with a forward link from the top for discoverability. The Iron Law now appears at line fifty-one. The original tuned content reads first; the new content sharpens but does not displace.

The sixth hard decision was about the Mandatory Response Format mechanism. There were two reasonable places to put it: inside the karpathy-guidelines skill (as another rule), or as a separate file that gets appended to CLAUDE.md (preamble level). We chose the latter for a specific reason: the format produces *visible artifacts* at the end of every response. It is not a behavior-shaping rule; it is an output-shaping rule. Output shaping belongs at the preamble level because it has to fire after every skill, not within any one of them. The format's job is to make the discipline of the four Karpathy rules visible — every response that modifies code has to enumerate its assumptions, with critical markers on the load-bearing ones, and list any bugs noticed in adjacent code without fixing them. That visibility is what turns invisible discipline into a reviewable artifact.

The seventh hard decision was about the Ubiquitous Language ritual placement. We could have created a new top-level skill for it (paralleling Matt Pocock's grill-with-docs). We could have folded it into using-superpowers (since CONTEXT.md is read at session start). We chose to fold it into brainstorming. The reason: the discipline of naming things is design discipline, and brainstorming is the skill that owns design. The read-at-session-start rhythm is incidental; the real action is during the design conversation, when terms get pinned down. The cross-references from executing-plans, receiving-code-review, and systematic-debugging are minimal — one line each — because those skills do not own the vocabulary, they just consult it.

The eighth hard decision concerned what *not* to add. There is a temptation, when you are building a behavior-shaping library, to add behavior-shaping rules for every failure mode you have ever seen. We deliberately rejected several candidate additions. A rule about commenting code (Karpathy's "default to no comments" guidance is in the karpathy-guidelines skill, not separately reinforced everywhere). A rule about preserving formatting (out of scope; that is a code-style concern, not a behavior-shaping concern). A rule about explicit error handling (the existing skills already cover this implicitly through the Iron Law and the Mandatory Response Format). A rule about commit hygiene (the existing finishing-a-development-branch skill already covers this). Each of these would have been *correct* additions; none of them passed the bar of "no existing skill has the right semantic ownership of the problem." Restraint was harder than addition.

The ninth hard decision was about the personal engineering standard as a separate document. We could have folded it into the karpathy-guidelines skill. We could have made it a new skill. We chose to make it a CLAUDE_APPEND.md file at the project root, with a note that it should be appended to user-global or project-level CLAUDE.md. The reason: the Mandatory Response Format is a personal standard, not a universal one. It is opinionated about what every response should look like. Putting it in a skill would have made it auto-trigger as if it were universally correct discipline. Putting it in a CLAUDE.md append makes its scope explicit: this is *my* engineering standard; adopt it if it fits your work, ignore it if not. The file makes its assumed context explicit at the top — assumes the Karpathy guidelines and Superpowers skill set are in effect; adds only what they do not cover.

## Part Six: Validation — The Eval Loop

The hardest part of forking a behavior-shaping library is that you cannot validate your changes by reading them. The whole point of the library is to shape agent behavior under fresh-session conditions, where the agent has no memory of your design intent and only the skill content to work from. Logic and craft can produce ambitious, coherent skills that do not actually fire in practice. The upstream Superpowers maintainers had been explicit about this in their contributor guidelines: skills are not prose, they are code that shapes agent behavior, and PRs that modify them without before-and-after eval evidence get rejected. That bar applies internally to the fork even though we are not submitting upstream.

So after the additions were complete, we built an acceptance harness. It lives at `docs/superpowers/evals/acceptance.md`. It is not an automated test suite — those are not feasible against an LLM whose output is non-deterministic. It is a structured probe-and-observe harness. A human operator opens a fresh Claude Code session, sends the exact probe message verbatim, captures the response, scores it against an expected-behavior checklist, and notes any surprises. Seven probes, each targeting a different behavioral addition. Each probe has an expected-behavior checklist with specific, observable predictions. Each probe has an Observed block for pasting the transcript. Each probe has a Surprises slot for things the design did not predict. The harness assumes the operator runs probes honestly — somebody who fills in expected output without running the probe is gaming the harness, not validating it.

The first probe targets the brainstorming skill. The probe message is exactly six words: *Let's design a small order book for an A-share trading system.* The expected behaviors are: the brainstorming skill announces and fires; the agent globs for CONTEXT.md and offers lazy creation if absent; the agent disambiguates the word "order"; the agent does not immediately propose a design (the brainstorming skill has a hard gate against jumping to implementation); the agent offers a Walking Skeleton as the first design deliverable for this greenfield system; and at least one Karpathy rule gets surfaced as a lens.

We ran probe one. The result was instructive in a way I did not expect.

In the first run, the agent did not announce any skill. It went straight into a design recommendation, listing the A-share-specific concerns (price-time priority, tick sizes, call auctions) and proposing a continuous-auction limit-order book as the toy. The response was technically competent — the model has plenty of A-share domain knowledge — but it was *without-skill* behavior. The brainstorming skill had not auto-triggered at all. Investigating, the cause was install state, not skill content: the user was running Claude Code in a VSCode extension where the `/plugin` command was not available, so the fork had never been installed. The skill content was not in effect.

We addressed this by junction-installing the skills directly into `~/.claude/skills/` — a Windows directory junction equivalent to a symlink, which does not require admin privileges. The skills now auto-trigger via their description field even without the full plugin's SessionStart hook. We re-ran probe one in a fresh session. This time the agent announced `brainstorming skill` immediately, globbed for CONTEXT.md, found none and noted lazy creation, and asked a clarifying multiple-choice question about what kind of order book the user meant (educational, backtest, research-grade, production). The hard gate held. The Ubiquitous Language ritual surfaced — though in a form that surprised us, which we will come back to.

Probe one took five turns to reach the design-presentation step. The agent asked about rule subset (call auctions and price limits in scope or not), about interaction model (library, CLI, or both), about time model (wall clock or simulated). Each question was a multiple-choice with a recommended answer. Each one was materially design-relevant — the time-model question, for example, directly shaped the Walking Skeleton's testable boundary. We were prepared to flag five clarifying questions as drag, but on inspection none of them was wasted. The agent self-bounded after question five and transitioned to design presentation.

At design presentation, the original Walking Skeleton trigger failed. The agent went straight into Section 1: module layout, core data model, OrderBook class. No skeleton. We had predicted this exact failure mode in the original evaluation — *"Walking Skeleton is greenfield-only but the guard is soft. The skill says 'Don't apply this when...' That's a judgment call, and LLMs are poor at judgment calls without hard rules."* Predicted, materialized.

The fix was small. The Walking Skeleton lived in its own subsection at line thirty-four of the brainstorming skill. The checklist step that the agent actually executed at line seventy-six did not reference it. Attention-budget failure. We pulled the trigger into the checklist step itself as a Greenfield Gate clause: *if the user's request describes a new system, service, project, library, codebase, or product that does not already exist on disk, the first section MUST be a Walking Skeleton; no data-model section, file layout, or component breakdown may be presented before the Walking Skeleton is presented and approved; skipping this step is a failure of the skill.* We also rewrote the subsection's own trigger from descriptive ("When the design is for a new system or service") to directive ("TRIGGER — no judgment call: apply this whenever...").

We re-ran probe one in a third fresh session. This time, after the user confirmed Python and Tier 2 rule scope, the agent said — directly quoting the transcript — *"Greenfield, so I'll lead with a Walking Skeleton after we pin scope."* That sentence is the trigger firing. The agent acknowledged the gate, named the upcoming deliverable, and proceeded.

After three more clarifying turns, the agent presented the Walking Skeleton in textbook form. Six numbered happy-path steps from CLI invocation through trade output. Five concrete seams — a Clock protocol with simulated and wall implementations, an Order dataclass, a Trade dataclass, a MatchingEngine class with stubbed submit and cancel methods, a replay CLI signature — each defined concretely enough to compile or type-check. One acceptance test in full pytest code, with a golden-file diff. And an explicit list titled *What this skeleton deliberately does NOT have yet*, naming auction phases, price limits, lot size, the real book data structure, cancel logic, and multi-symbol handling, each annotated as plugging into an existing seam later. That last list is the Walking Skeleton concept understood at depth, not just surface-mimicked. The agent had internalized what a skeleton is *for* — validating wiring, deferring business logic — not just its shape.

Probe one passed on the second attempt, with the targeted fix validated cleanly. That is the eval loop working as designed: a real failure mode caught, a surgical fix applied, a re-run confirming the fix.

The third probe targeted the test-driven-development skill's Test Quality Bar. The probe message presents a function and a single shallow test: a `calculateDiscount` function that returns 80 percent of price for premium customers, with a test asserting that `calculateDiscount(100, true)` returns 80. The expected behaviors: the agent identifies the test as shallow, applies mutation thinking, proposes at least one additional test with a different input.

The first run was strong on content. The agent identified the missing non-premium branch coverage, applied mutation thinking explicitly (a bug like an inverted ternary would still pass), proposed two additional tests, and criticized the test name as too generic. But the response did *not* announce the test-driven-development skill the way the brainstorming and prefer-deterministic-code skills had announced themselves. The skill content shaped the output, but the skill itself was not visibly triggered.

The diagnosis: a description coverage gap. The skill's description was *Use when implementing any feature or bugfix, before writing implementation code*. A *review* question — "is this test good enough?" — does not match the trigger semantically, even though the skill body has a Test Quality Bar section explicitly designed for review. The fix was to broaden the description with an OR clause: *Use when implementing any feature or bugfix before writing implementation code, OR when reviewing tests for quality, coverage gaps, or shallowness (e.g. 'is this test good enough?', 'should I add more tests?', 'this test passes but feels weak')*. Concrete example prompts in parentheses, because the skill auto-trigger matches against intent signal — adding the exact phrasings most users would write makes the match much sharper than abstract terms like "review."

We re-ran probe three in a fresh session. The agent now announced `using-superpowers skill` and `test-driven-development skill` at the top, referenced "the Test Quality Bar checklist" by name, and produced a sharper analysis than the first run. Where the first run had given one mutation case (inverted ternary), the second gave three (hardcoded return, branch mutation, rate change). Where the first run had proposed additional tests, the second proposed *paired* premium tests at different prices — to distinguish multiplication (`* 0.8`) from subtraction (`- 20`), since a single data point at price 100 cannot tell the two apart. That second improvement is mutation thinking applied at the rule-versus-coincidence level, not just the assertion level. The fix did not just trigger the skill; it triggered the skill *more thoroughly*. Second clean fix-validate cycle of the eval.

The fourth probe targeted prefer-deterministic-code. The probe message proposed using an LLM to classify webhook events by their `event_type` field, when the event types are a known finite set (`user.created`, `order.placed`, `payment.completed`). The expected behaviors: the agent refuses, identifies the question as deterministic, proposes a dictionary or match solution, gives reasoning that cites reliability, cost, or determinism. The response was a clean pass with no caveats. The agent announced the skill, refused the LLM approach, gave a three-axis argument (determinism, cost-and-latency, failure-mode), and offered a Python `HANDLERS` dictionary with `.get` and a fail-loudly clause. It also incidentally demonstrated the Mandatory Response Format — appending an Assumptions Made section with a critical marker, omitting Discovered Issues because none were found. That signal — the format firing automatically, without explicit prompting — was the indirect validation of Probe 7.

The fifth probe targeted writing-plans' Architecture Contracts First rule. The probe message: *I've approved this spec: "Build a RateLimiter service that allows up to N requests per window per key, with pluggable storage backends." Please write the implementation plan.* The expected behaviors: writing-plans invoked, Task 1 defines the RateLimiter interface, Task 2 is a boundary test, implementation comes after the contract is fixed, the storage backend is also contract-first.

The response was the strongest single artifact the eval produced. The agent first surfaced six load-bearing assumptions before writing the plan — language, algorithm, backends, API surface, concurrency scope, output path — and asked for confirmation. That is Karpathy Rule 1 firing per the skill's own Karpathy Reinforcement block: *surface assumptions about scope, constraints, and intent in the plan itself; ambiguity left in the plan becomes ambiguity in execution.* When the user confirmed, the agent wrote a 763-line plan with 13 tasks, no placeholders, every test paired with concrete code, every step with a runnable command and an expected output. Task 1 was project bootstrap (package.json, tsconfig, vitest config). Task 2 defined the contract: a `Store` interface with a single `incrementAndGet` method, a `StoreEntry` type, a `RateLimitResult` type, a `LimiterOptions` type — verified by `tsc --noEmit` only, no behavior yet. Task 3 was a programmable test double for unit tests. Tasks 4 through 7 implemented and tested the RateLimiter against the test double. Tasks 8 through 11 implemented MemoryStore under TDD. Task 12 was an integration test exercising the real limiter against the real memory store. Task 13 was the public barrel export. The plan ended with a Done Criteria section listing observable success conditions: typecheck exits zero, test counts per file, thirteen commits, public surface limited to specific named exports.

The plan also concluded with the Mandatory Response Format: a Discovered Issues section correctly stated as empty (no adjacent code to triage), and an Assumptions Made section with critical markers. The strict reading of the eval said Task 1 should be the contract; instead Task 1 was bootstrap and Task 2 was the contract. That is a defensible reordering — bootstrap is a prerequisite that produces no behavior, and the first behavioral artifact is in fact the contract — but if we wanted strict compliance we could move bootstrap to a Task 0 or implicit step. We marked this as a soft-miss rather than a fail.

By the end of the eval cycle, five distinct behavioral additions were validated: Walking Skeleton (the greenfield trigger, after one fix), Ubiquitous Language (the CONTEXT.md attempt and within-domain disambiguation), Test Quality Bar with mutation thinking (after one fix), Architecture Contracts First (the interface-before-implementation ordering), and the Mandatory Response Format (firing automatically without explicit trigger). Five of seven probes complete; two unrun because they required setup we did not have at hand — a real bug in a real codebase for the brownfield probe, and a small executable plan for the Checkpoint Discipline probe.

The eval surfaced one persistent soft-miss that the fixes did not address: the Karpathy rules fire *behaviorally* but are not always cited *by name*. The agent surfaces assumptions because the design demands it; the agent prefers simplicity because the skill body says so; the agent makes surgical changes because the executing-plans skill enforces it. But the response rarely says, in so many words, "by Karpathy Rule 1 I am surfacing this assumption." We made a deliberate choice not to fix this by demanding rule-naming in the skill bodies. The behavior is what matters; the citation is bureaucratic.

## Part Seven: Lessons and Open Questions

A few lessons came out of this work that I think generalize beyond this fork.

The first is that *eval loops catch real failure modes that intuition misses*. We had identified the soft Walking Skeleton trigger as a risk in the very first round of design review — I wrote in the original evaluation document that "Walking Skeleton is greenfield-only but the guard is soft; LLMs are poor at judgment calls without hard rules." That sentence was sitting in the evaluation, in front of me, when I shipped the original Walking Skeleton subsection with soft trigger language. The intuition was correct; the application was not. Only an actual fresh-session probe forced the fix. This is the value of evals: they make you act on the things you already knew but had not committed to changing.

The second lesson is that *soft trigger language does not survive LLM attention budgets*. A subsection deep in a skill body, gated by "when the design is for a new system or service," will not reliably fire even when the condition is met. The model reads the skill, complete the checklist, and the subsection's guidance drifts out of working attention by the time it matters. The fix is to pull triggers into the checklist itself, in directive language with no judgment call required. A clause that says "if X, then MUST Y" beats a paragraph that describes when Y applies.

The third lesson is that *description coverage matters more than skill body content*. Auto-triggering is the entire mechanism by which a skill body gets read. If the description does not match the user's intent, the body does not fire, no matter how good its content is. We had a Test Quality Bar section explicitly designed for review questions and a skill description that only mentioned implementation. The body was dead weight for review use cases until the description was broadened. The cheapest, highest-leverage fix in a skill library is often the description, not the body.

The fourth lesson is that *the Ubiquitous Language ritual produces unexpected forms*. We had designed for cross-domain disambiguation — "do you mean trading order, purchase order, or work order?" In practice, when the user said "order book for an A-share trading system," the agent's within-context interpretation was unambiguous (this is clearly a trading order) and what fired instead was *within-domain* disambiguation: "do you mean an exchange-side matching engine, a broker-side order management system, a market-data reconstruction view, or a backtesting order book?" That within-domain disambiguation is *more useful* than the cross-domain version. The skill was doing the right thing by a different mechanism than its rule prescribed. We amended the harness to reflect this rather than amending the skill to enforce a less useful pattern.

The fifth lesson is that *distributing discipline across multiple skills works*. The Architecture-Driven Design harness operates at three different points in the workflow: greenfield design (Walking Skeleton in brainstorming), task decomposition (Contract-First in writing-plans), test ordering (outside-in in TDD). Each piece fires at the moment when that decision is being made. The alternative — concentrating all of ADD in a single skill — would have produced an overloaded skill with poor attention-budget characteristics. Three checkpoints, three skills, three moments of enforcement.

A few questions remain genuinely open. The Karpathy-rule-naming gap: should the skill bodies demand explicit rule citation, or is behavioral compliance sufficient? My current position is that behavior is what matters and citation is bureaucratic, but I have low confidence in that. A study where the same probe runs with rule-naming required and without it would settle it. We have not run that study.

The Checkpoint Discipline self-check has not been validated end-to-end. The skill body has the right structure — a four-line Done/Verified/Remaining summary, a three-item self-check before starting step N+1 — but Probe 6, which would exercise it, requires a small executable plan we have not constructed. Until that probe runs, the discipline is logically motivated but not measured.

The brownfield bug-fix probe (Probe 2) is unrun for similar reasons. It requires a repo with a real login endpoint that has a real empty-password bug. Constructing that probe environment is cheap but takes time. Without it, we cannot confirm that the Walking Skeleton trigger correctly *suppresses* itself for non-greenfield work — a different failure mode than the original miss, but a real one.

The token-budget-discipline skill auto-triggers on its description, but its integration with executing-plans and systematic-debugging relies on cross-references that we added but have not eval'd. Whether those cross-references actually pull the budget skill into the relevant flows is unknown. The fix would be a probe that runs a long debugging session and observes whether the budget skill ever fires.

The fork has not been tested on weaker models. The whole design assumes Sonnet-or-Opus-class capability, where the skill body shapes behavior reliably. A smaller model might read the skill and fail to act on it. Without testing, the fork's effective floor is unknown.

Despite these open questions, the fork has crossed an important threshold: from *logically motivated* to *validated under fresh-session probing*. Five distinct behavioral additions fire reliably. Two surgical fixes have been applied based on real eval findings, and both fixes have been re-validated. The skill library is small (three new skills, modifications to thirteen existing skills, one preamble file). The motivations are coherent and address documented failure modes that the upstream library did not encode. The eval harness is reusable for future changes — any future modification to the skill bodies can be measured against the same probe set, with new probes added for new behaviors.

The deeper lesson, the one that I think will outlive this specific fork, is that *behavior-shaping libraries for AI agents are testable artifacts*. They are not prose; they are code. They have failure modes that can be observed in fresh sessions, fixes that can be applied to skill bodies, and re-validation cycles that produce evidence. The fork's contribution is not just the three motivations and their inline expressions; it is the demonstration that this kind of work *can* be evaluated rigorously, in finite time, with cheap tools — a Markdown file, a probe message, an honest observer.

That, in the end, is what makes me hopeful about this style of work. The first generation of AI-coding tools focused on what the agent could *do*: invoke tools, edit files, run commands. The second generation, which this fork tries to push forward, focuses on what the agent *should* do: surface assumptions, refuse premature complexity, validate architecture before features, name domain terms canonically, bound long loops with checkpoints. That second-generation work is harder to validate than the first, because the outcomes are about how the agent reasoned, not just whether it completed a task. But the eval harness shows it is not impossible. A handful of well-chosen probes, fresh sessions, honest observation, and iterative fixes — that is the loop. It worked here. It will work elsewhere.

For anyone who wants to use this fork: the installation paths are in the README, both the standard `/plugin install` route and the junction/symlink alternative for environments where `/plugin` is not available. The verification probe is the same one the eval used; if `brainstorming` announces and fires correctly on "Let's design a small order book for an A-share trading system," the install is in good shape. The full eval harness is at `docs/superpowers/evals/acceptance.md`. The original Superpowers project, the Karpathy guidelines, the CONTEXT.md format, and the Karpathy observations themselves are all attributed in the README. All upstream content is MIT-licensed. The fork is also MIT-licensed.

The work continues. The Karpathy-rule-naming question is the next thing I want to study. The brownfield probe will get built when the next real bug shows up in a project I am working on. The Checkpoint Discipline probe will get built when the next implementation plan is non-trivial enough to make it worthwhile. The token-budget-discipline integration will get a probe when I next find myself in a debugging session that runs long enough to test it.

For now, the fork ships with the discipline baked in, the evidence documented, the failure modes named, the fixes traceable, and the harness reusable. That seems like a reasonable place to stop and let other people use it.
